# 3단계 리뷰: CI/CD와 빌드의 결합

> 작성일: 2026-10-03
> 실습 위치: `practice/week3/`, `.github/workflows/week3-ci.yml`
> 목표: 3-1 ~ 3-4에서 만든 파이프라인을 정리하고, SDV 통합 빌드 관점에서 한계를 짚어 4단계로 연결한다.

## 1. 완성된 파이프라인

```
push / PR / 수동 실행
   │
   ▼
┌─ 러너 (ubuntu-24.04, 매번 새 VM) ───────────────────────────────────────────┐
│ Checkout                                                                   │
│ Restore Bazel cache      ← 3-4  disk / repository / bazelisk 캐시 복원       │
│ Show Bazel version       ← 3-1  .bazelversion(9.2.0) 고정 확인               │
│ Show environment         ← 3-2  OS·gcc 기록 (로컬과 비교할 근거)              │
│ Build  --config=ci       ← 3-1  + 3-4 --profile                              │
│ Build profile summary    ← 3-4  단계별 시간 / 상위 작업                       │
│ Toolchain info           ← 3-2  실제로 사용된 컴파일러 확인                   │
│ Test   --config=ci       ← 3-1  종료 코드로 PASS/FAIL                         │
│ Upload test reports      ← 3-3  if: always() — 실패해도 로그 보존             │
│ Package --config=release ← 3-3  pkg_tar + stamping(git 커밋·dirty·버전)       │
│ Upload package           ← 3-3  app-0.1.<run>-<sha> 아티팩트                  │
└────────────────────────────────────────────────────────────────────────────┘
```

### 저장소에 고정한 "빌드 환경"

| 파일 | 고정하는 것 | 도입 |
|---|---|---|
| `.bazelversion` | Bazel 버전 | 3-1 |
| `MODULE.bazel` + `MODULE.bazel.lock` | 외부 의존성 버전·해시 (`--lockfile_mode=error`로 강제) | 3-1, 3-2 |
| `.bazelrc` | 로컬/CI/릴리스 빌드 옵션 | 3-2 ~ 3-4 |
| `week3-ci.yml` `runs-on` | 러너 OS 이미지 | 3-2 |
| `.gitattributes` | 셸 스크립트 줄바꿈(LF) | 3-3 |
| `--repo_env=PATH` | 툴체인 자동 감지가 보는 환경 | 3-4 |

## 2. 단계별 핵심 교훈

| 단계 | 실험 | 교훈 |
|---|---|---|
| 3-1 | 로직 오류 vs 문법 오류 push | build와 test를 나누면 실패 원인과 책임 소재가 바로 드러난다. 경로 필터(`paths:`)는 사람이 관리하는 추측이고, 정확한 영향 분석은 `rdeps`가 한다 |
| 3-2 | 절대 경로 테스트 (로컬 PASS / CI FAIL) | 샌드박스는 워크스페이스 안의 미선언 파일만 가린다. 선언한 입력과 실제 입력이 같아야 한다. 컴파일러는 기본적으로 고정되지 않는다(호스트 gcc 자동 감지) |
| 3-3 | 패키징·stamping·실패 시 아티팩트 | 검증되지 않은 바이너리는 아티팩트로 남기지 않는다. stamping은 릴리스에만 적용한다(캐시와 충돌). dirty 빌드는 추적성을 깨뜨린다 |
| 3-4 | 캐시 적용 → 효과 없음 → 프로파일 | 캐시는 실행 단계만 줄인다. 환경 감지 결과는 캐시할 수 없다. 측정해서 병목을 찾는다(rules_swift 36초 → PATH 고정으로 Build 50초 → 8초) |

**관통하는 원칙**: CI의 가치는 깨끗한 환경에서 **빌드가 선언하지 않은 입력**을 드러내는 데 있다. 실패(3-2)든 성능(3-4)이든 해결책은 같다. 환경을 명시적으로 선언하고 고정한다.

## 3. SDV 관점 스트레스 테스트: 지금 구조는 어디서 무너지는가

| SDV 상황 | 지금 파이프라인 | 무너지는 지점 | 필요한 것 | 연결 |
|---|---|---|---|---|
| **멀티 타겟** (Cortex-M MCU + Cortex-A HPC + x86 시뮬레이션) | 호스트 gcc 하나로 x86만 빌드 | 타겟마다 다른 컴파일러가 필요하다. 호스트 자동 감지로는 ARM 바이너리를 만들 수 없다 | Bazel `platforms` + 해시로 고정한 hermetic 크로스 툴체인, 타겟별 build matrix | 4-1, 5단계 ① |
| **공급업체 코드 통합** (Tier1/Tier2, 일부는 바이너리로만 제공) | 한 저장소, 한 팀 | 다른 저장소·다른 조직의 변경이 `paths:` 필터에 걸리지 않는다. 소스 없는 `.a`는 재빌드·추적이 어렵다 | 외부 모듈로 버전 고정(bzlmod), 인터페이스(ARXML) 계약, `rdeps` 기반 영향 분석 | 4-2, 5단계 ② |
| **변형(Variant) 관리** (차종·트림·지역별 기능 조합) | 빌드 설정 1종 | 조합 수만큼 build/test 횟수가 늘어난다 | `config_setting`/`select`, 플랫폼 조합, 변형별 캐시 공유 | 4-2 |
| **규모** (수백만~수천만 LOC) | `actions/cache` (통째로 다운로드, 저장소당 10GB) | 캐시 다운로드가 빌드보다 길어진다. 러너 한 대의 CPU로는 부족하다 | `--remote_cache` + `--remote_download_minimal`, 원격 실행(RBE) | 4-4, 5단계 ③ |
| **기능안전·추적성** (ISO 26262) | 7일 보관, stamping은 기록만 함 | 보관 기간이 짧다. dirty 빌드를 막지 않는다. 툴체인이 기록되지 않는다 | 불변 아티팩트 저장소(장기 보관), dirty·미서명 릴리스 차단 게이트, 툴체인 해시 기록 | 4-3 |
| **사이버보안·공급망** (ISO/SAE 21434, UN R155) | 116개 모듈을 끌어오지만 목록이 없다 | 바이너리에 무엇이 들어갔는지 증명할 수 없다 | 빌드 그래프에서 SBOM 자동 생성 | 4-3, 5단계 ④ |
| **OTA 업데이트** (UN R156) | tar 하나 | 차분 업데이트, 버전 호환성, RXSWIN 관리가 고려되지 않았다 | 재현 가능한 바이너리(차분 크기 최소화), 버전 메타데이터 | 4-4 |

## 4. 3단계에서 보류한 것

- 컨테이너 잡(`container:`), hermetic C 툴체인: 개념만 다룸 → 5단계 크로스 컴파일에서 실습
- 원격 캐시 서버 연결(`--remote_cache`): 개념만 다룸 → 5단계 ③
- dirty 릴리스 차단 게이트: 아이디어만 제시
- `Extracting Bazel binary`(약 2초) 캐시: 효과가 작아 보류
- (2단계에서 이어짐) 원격 실행(RBE), 멀티 언어(`py_library` 등) 실습

## 5. 복습 질문과 답안 요점 (자율 복습용)

**Q1. 공급업체 라이브러리가 `/opt/vendor_a/config.xml` 절대 경로를 몰래 읽는다면?**
- 3-2의 `config_test`와 같은 구조다. 샌드박스는 시스템 절대 경로를 가리지 않는다.
- 개발자 PC나 공급업체 환경에 그 파일이 있으면 로컬에서는 통과한다. 깨끗한 CI 러너에서 그 코드 경로를 실행하는 **테스트가 있을 때만** 드러난다.
- 해당 경로를 실행하는 테스트가 없으면 CI도 통과하고, **차량(타겟 ECU)에서 처음 터진다.** 빌드 성공이 곧 동작 보장은 아니다.
- 대응: 공급업체 코드도 `data`/`deps`로 입력을 선언하게 하는 계약, 공급업체 컴포넌트 단위의 hermetic 테스트, 가능하면 소스 수령.

**Q2. stamping과 캐시의 충돌을 지금 BUILD 구조가 어떻게 줄이는가?**
- git 정보는 작은 `:build_info`(텍스트 파일)에만 들어간다. `:app` 바이너리는 stamping과 무관해서 커밋이 바뀌어도 소스가 같으면 캐시에서 나온다.
- 매번 다시 실행되는 건 `:build_info` 생성과 `:app_pkg` 묶기(수 밀리초)뿐이다. **변하는 부분을 그래프의 끝(leaf)으로 격리**한 구조다.
- 반대로 버전 문자열을 `main.c`에 `-D` 매크로로 넣었다면 `app`, 그리고 그걸 쓰는 모든 것이 매번 다시 빌드된다.

**Q3. 5년 뒤 `app-0.1.9-ace2e22…`를 똑같이 다시 만들 수 있는가?**
- 가능하게 하는 것: `BUILD_INFO.txt`의 커밋 SHA → 소스 복원, `.bazelversion`/`MODULE.bazel.lock` → Bazel·의존성 버전과 해시 복원, `.bazelrc` → 빌드 옵션 복원, `__DATE__` redacted·`pkg_tar` mtime 고정 → 시각에 따른 차이 제거.
- 방해하는 것:
  - `retention-days: 7` → 원본 바이너리 자체가 이미 없다(비교 대상 소실)
  - 호스트 gcc 자동 감지 → 5년 뒤 러너의 gcc가 다르면 바이너리가 달라진다
  - `ubuntu-24.04` 러너 이미지 → GitHub가 지원을 종료하면 사라진다. 이미지 안의 glibc/binutils도 그사이 업데이트된다
  - 외부 다운로드(BCR, GitHub 릴리스 URL) → 5년 뒤에도 남아 있다는 보장이 없다(미러·벤더링 필요)
- 결론: 지금 파이프라인은 "소스와 의존성 버전"까지는 복원할 수 있지만 "툴체인과 실행 환경"은 복원하지 못한다. 컨테이너 이미지와 hermetic 툴체인을 해시로 고정해 **아티팩트와 함께 장기 보관**해야 한다 → 4-3, 5단계.
